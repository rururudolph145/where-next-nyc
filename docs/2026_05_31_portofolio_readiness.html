Why This Rewrite Scope Discipline

The previous checklist enumerated every gap. That framing accidentally turns the portfolio into an infinite TODO list. This rewrite reframes it around five demo tiers, each independently shippable. The senior-engineer signal a hiring manager looks for is not "did this person build everything?" — it's "did they decide what to stop building, and explain why?"

Therefore: ship the first two tiers polished, document the rest as scoped future work. A "Future Work" section that explains drift detection, model registry promotion, and Kubernetes deployment in design terms scores higher in interview signal than half-built YAML.

The Five Demo Tiers 2 Shipped / 1 Next

Each tier is a self-contained demonstration. A reviewer can stop at any tier and have a coherent story. There is no implied "more is better" — fewer tiers, each polished, beats more tiers half-finished.

Tier 1 — Static MVP demo Shipped · demoable today
Reviewer test: uv run → curl /heatmap → ranked predictions with baseline lift, /health, model version.
The driver-facing question — "where will demand be 30 minutes from now" — is answered end-to-end on a static historical dataset. Bronze → Silver → Gold pipeline, LightGBM validated against a last-week-same-hour baseline, FastAPI heatmap endpoint with fallback to the last approved model.
Includes: PBI 1–3 · B0/B1/B2 · PBI 12–14 · PBI 18 (baseline + recall@K) · PBI 19 (Pandera) · PBI 20 (registry gate) · PBI 21 (fallback) · PBI 22 (prediction log) · PBI 27 (/health) · PBI 30 (CI)
Tier 2 — Live cadence (compressed-clock production sim) Next — one PBI
Reviewer test: DEMO_MODE=1 make demo → heatmap visibly refreshes every ~2 seconds of wall-clock as 15 simulated minutes elapse. Midtown lights up at simulated 5pm; JFK at simulated 6am.
Adds no ML capability — adds operational realism. The system stops being a one-shot script and becomes a continuously-refreshing service driven by an injected Clock. Because TLC data has a 1–2 month publication lag, "live" production is honestly impossible from a portfolio repo; a deterministic, compressed SimulatedClock exercises the exact same code path production would. This is the version of the demo that wins SmartNews / Google L4 interviews, because it shows the system is operationally coherent under time — not just a model wrapped in a Flask call.
Shipped: PBI 25a (Clock + skeleton). Open: PBI 25b (refresh_15min_dag) — the single PBI that unlocks Tier 2.
Tier 3 — Self-retraining loop Scoped — write up, don't build
Reviewer test: trigger a training run → see PBI 20 gate either promote or reject the challenger → if rejected, the previous model continues serving (visible in /model-info).
The training loop already functions as library code: PBI 20's champion-vs-challenger gate and PBI 21's inference fallback are both live. Wrapping them in an Airflow DAG (PBI 25c) is operational polish, not new capability. Drop the DAG; document the wrapper in README "Future Work". Demonstrating the gate + fallback by running the training script directly is sufficient interview signal.
Drop from build queue: PBI 25c. Already shipped under the hood: PBI 20, PBI 21.
Tier 4 — Closed feedback loop (drift → retrain) Scoped — write up, don't build
Reviewer test: inject synthetic drift → detector flags it → alert writes retrain_required marker → monitor DAG triggers training DAG → new model goes through the gate.
Drift monitoring on a finite historical dataset is largely theatre — there is no real drift to detect on TLC parquets you've already seen. The prediction log (PBI 22) exists as the data foundation, which is enough to talk about closed-loop monitoring in interviews. Do not build Evidently wrappers, alert files, or the monitor DAG. Write a "Future Work" paragraph explaining the design instead — that paragraph carries the same signal at 1% of the build cost.
Drop from build queue: PBI 23 (Evidently) · PBI 24 (alerts) · PBI 25d (monitor DAG). Shipped foundation: PBI 22.
Tier 5 — Business-value proof (driver-agent harness) Optional — highest-value post-MVP
Reviewer test: open docs/simulation_results.md → see HeatmapFollower vs LastWeekFollower vs Stationary on a held-out week — trips served, % idle, miles to pickup, total fare.
Everything up to Tier 4 proves the system works. This is the only piece that proves the product works — that drivers who follow the heatmap are measurably better off than drivers who follow last-week's pattern. If interview prep time allows exactly one post-Tier-2 PBI, this is the one: it converts "the model has lift on WAPE" into "drivers using it earn more dollars." The slide that wins the interview conversation.
Open: PBI 28 (driver-agent simulation harness). Depends on PBI 18 (baseline policy) + PBI 25a (SimulatedClock) — both shipped.
Tier 6 — Personalised ranking Deferred — README only
Reviewer test: GET /recommend?lat=&lon= instead of /heatmap — top-N zones ranked by predicted demand divided by travel cost.
Promotes the heatmap (Uber model) to ranked per-driver recommendations (DiDi model). Mentioned in the README as future work; not built. Documenting the design trade-off ("heatmap leaves interpretation to the driver; ranking centralises it but requires fleet-state tracking to avoid herding") is itself interview signal — no code required.
Deferred entirely: PBI 5 · PBI 6 · PBI 7 · PBI 8.

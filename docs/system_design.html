Problem Formulation

Objective: High-Demand-Zone Heatmap

Maximize driver efficiency by telling the driver high-demand zones at t+30 and t+60 minutes. Using the system, the driver will be able to decide where they should go given their current position.

Step 1: Functional Requirements

#RequirementDerived from
F1 Predict trip demand per zone at t+30 and t+60 "high-demand zone in t+30 and t+60 minute"
F2 Serve predictions as a heatmap to the driver "telling the driver high-demand zone"
F3 Refresh predictions periodically so they stay current "t+30 and t+60" implies relative to now

Step 5: Separate the Loops

Not everything runs at the same frequency. Group by cadence:

FrequencyWhat RunsWhy
Continuous Trip data ingestion into DB Events arrive as trips complete
Every 15 min Feature query + inference + update predictions store Heatmap freshness target
Days / weeks Model retraining (full pipeline) Model drift is slow; seasonal patterns
On request API serves latest predictions Driver opens app
Key insight: decouple the loops

Each loop runs independently at its own cadence. The inference loop doesn't need streaming — prediction is batch by nature because the model needs aggregates over completed time windows (e.g., trip count in the last hour). You can't compute trip_count_lag_1 until that hour is over.

B Feature Computation

The model needs trip_count_lag_1 = "how many trips in zone X in the hour ending 1 hour ago." This is a SQL aggregation:

SELECT pulocationid,
       COUNT(*) as trip_count,
       date_trunc('hour', pickup_time) as hour
FROM trips
WHERE pickup_time BETWEEN (now - 168h) AND now
GROUP BY pulocationid, hour

Then compute lag features, cyclical time features, and join zone coordinates. Output: one feature row per zone (~260 rows).

Data Source Reality & Simulation Strategy

Real world vs MVP data source

Key distinction

The Socrata API is a historical data archive, not the actual production data source. In production, there is no API call — data arrives organically as drivers complete trips and submit trip records through the app.

ProductionCurrent MVPSimulation (target)
Data source Driver submits trip → event lands in DB Socrata API bulk download → Bronze Raw folder (historical trips partitioned by day)
Arrival pattern Continuous, second-level granularity Bulk (all months at once) Day-by-day replay with time filter
Pipeline trigger Cron every 15 min Manual script run Loop advancing simulated clock

Raw folder structure

Historical data is partitioned by month and day, mirroring how trip data naturally accumulates:

data/
  raw/
    yellow_tripdata/
      2021_01/
        2021_01_01.parquet
        2021_01_02.parquet
        ...
        2021_01_31.parquet
      2021_02/
        2021_02_01.parquet
        ...

This is the one-time seed step: download from Socrata, split into daily files, store in raw/. After this, the pipeline never touches the API again — it reads from raw/ just like production would read from a database.

Why second-level arrival doesn't matter

The model operates on hourly aggregates, not individual events

In reality, trip records arrive at second-level granularity — hundreds of events per minute across NYC. But the model's finest-grained feature is trip_count_lag_1: the total number of pickups in a zone during the previous completed hour.

This means:

  • Whether 500 trips arrive one-by-one over an hour or all at once in a bulk load, the feature value is the same: 500.
  • You can't compute trip_count_lag_1 until that hour window is fully closed.
  • Simulating per-second arrival adds infrastructure complexity with zero impact on features or predictions.
14:00:00  Trip A arrives    ┐
14:00:03  Trip B arrives    │
14:00:15  Trip C arrives    │  All contribute to the
  ...                       │  14:00-15:00 hour bucket
14:59:58  Trip Z arrives    ┘

15:00:00  Inference runs
          → queries: "how many trips in 14:00-15:00?"
          → answer: 500
          → same answer regardless of arrival pattern

What the simulation must get right

Must simulate correctlyWhy
Which trips exist at query time Inference must only see trips that have "already happened" relative to simulated time
Hourly window boundaries Features are hourly aggregates — the window must be complete before querying
Does NOT need to simulateWhy
Per-second arrival order Model uses hourly aggregates; individual event timing is irrelevant
Message queue / streaming infra A time filter on historical data produces identical features
Concurrent writes We read from static parquet files, not a live DB

Simulation approach

Simulated time = 2021-01-15 15:00

1. Read raw files: raw/yellow_tripdata/2021_01/2021_01_01.parquet
                   through 2021_01_15.parquet
2. Filter: keep only rows where pickup_time <= 2021-01-15 15:00
3. Run: clean → feature engineering → inference
4. Output: updated predictions store (heatmap for this moment in time)
5. Advance clock → repeat

A full month replays in minutes.
Same code path as a production cron job.
What to say in a design doc or interview

"In production, trip events stream into a database continuously at second-level granularity. However, the model's features are hourly aggregates, so per-event processing adds no value — inference runs as a periodic batch job on completed hourly windows. For demonstration, we replay historical data with a simulated clock and a time filter, exercising the same inference code path as a production cron job."

Known Limitations & Future Considerations

Feedback loop

Driver recommendations influence future trip data. If many drivers go to Zone A based on the heatmap, that zone becomes saturated. Not addressed in MVP since the heatmap approach (Uber model) mitigates herding naturally — drivers interpret the map differently and make individual decisions.

Multi-driver coordination

MVP serves the same heatmap to all drivers. DiDi-style per-driver optimization (different recommendation per driver to prevent oversaturation) requires fleet state tracking and is deferred to post-MVP.

Batch vs streaming inference

Prediction is batch by nature — the model needs aggregates over completed time windows (hourly trip counts). Data ingestion can be streaming into a DB, but inference runs as a periodic batch job. These two loops are decoupled. For demo, historical replay with a simulated clock exercises the same code path as a production cron job.

A/B testing

No framework for measuring if recommendations actually improve driver outcomes. A design doc for A/B test methodology is recommended before scaling to real users.
